формах:

|---|---|---|---|

| Задание | `week2/assignment.md` + `week2/assignment/` | индивидуальное задание: свои инструменты, свой цикл, метрики, A/B, отчёт | рубрика 100 баллов |

Обе части работают на **одних и тех же данных**: `week2/practice/poi.sqlite` — снимок

Один и тот же город, одни и те же таблицы, но разные задачи.

Сама идея недели: **агент — это модель плюс цикл**. Модель не «выполняет код», она
пишет «позвони функцию X с аргументами Y» (tool_calls), а выполняет вызов твой код и
возвращает результат модели наблюдением. Практика учит работать с этой механикой
через фреймворк, задание — написать тот же цикл руками, без фреймворка.

### Файлы недели и их роль

- `week2/practice/week02_agents.ipynb` — ноутбук практики (сама работа студента).

### Откуда взялся `sdk_tasks.py` и при чём тут `tasks.py`

Почти, но точнее так:

  - цены: `PRICE_IN=30`, `PRICE_OUT=120` ₽ за млн токенов и `cost_rub()`.
- **`tasks.py`** (в `week2/assignment/`) — файл, написанный **нами для задания**. Это не копия: заданию нужны **свои** десять вопросов, свой эталон и свои метрики (pass@1, A/B). ## Настройка (две обязательные ячейки)

**Ячейка установки** ставит `openai-agents`, клонирует репозиторий (для Colab).
Локально эта ячейка не нужна.

**Ячейка настройки** — самое важное из двух:

```python
SERVICE = "aitunnel"      # "openai" | "aitunnel" | "openrouter"
MODEL = "xiaomi/mimo-v2.6-flash"

os.environ["OPENAI_API_KEY"] = getpass.getpass("Ключ: ")
os.environ["OPENAI_DEFAULT_MODEL"] = MODEL

if SERVICE != "openai":
    set_default_openai_api("chat_completions")
    set_default_openai_client(AsyncOpenAI(api_key=..., base_url=BASE_URL, timeout=60.0))
set_tracing_disabled(SERVICE != "openai")
```

**Разбор «для чайника»:**
- Фреймворк `agents` (OpenAI Agents SDK) по умолчанию ходит в OpenAI: в их API
  Responses, их трассировку, их модель. Если ключ от посредника (AITunnel,
  OpenRouter) — всё это чужое и молча не работает. Поэтому мы **вручную** говорим
  SDK: использовать обычный `chat/completions` и наш `base_url`.
- `set_tracing_disabled(True)` — выключаем трассировку: чужой ключ в неё не
  пройдёт.
- `timeout=60.0` — чтобы запрос не висел десять минут, если сервис замёл.
- Результат в консоли: `настроено: xiaomi/mimo-v2.6-flash через https://api.aitunnel.ru/v1`.

**Почему везде `await Runner.run(...)`, а не `Runner.run_sync(...)`:** в ноутбуке уже
крутится event loop (это IPython), SDK честно отказывается работать вторым loop'ом.
Поэтому асинхронный запуск. В обычном скрипте `await` вне `async def` — ошибка
синтаксиса, в ячейке ноутбука — можно, IPython сам оборачивает в корутину.

## Задача 0. Разминка: один вызов без фреймворка

**Что было задачей.** Ничего писать не нужно: запустить ячейку и посмотреть, что
модель возвращает, когда её просят позвать инструмент.

**Код:**

```python
client = OpenAI(api_key=..., base_url=BASE_URL)
schema = {"type": "function", "function": {
    "name": "count_places",
    "description": "Сколько в городе мест такого вида. Возвращает одно число.",
    "parameters": {"type": "object", "required": ["kind"], "properties": {
        "kind": {"type": "string", "description": "вид места латиницей: pharmacy, cafe, outpost"}}}}}

answer = client.chat.completions.create(
    model=MODEL, tools=[schema],
    messages=[{"role": "user", "content": "Сколько в Ростове аптек?"}])

message = answer.choices[0].message
if message.tool_calls:
    call = message.tool_calls[0]
    print("модель попросила позвать:", call.function.name, call.function.arguments)
...
print("токенов:", answer.usage.prompt_tokens, "вход,", answer.usage.completion_tokens, "выход")
```

**Разбор «для чайника»:**
- `schema` — JSON, который мы описываем модели: «есть функция `count_places`, у неё
  один параметр `kind` — строка, вот описание». Это и есть **схема инструмента**.
  Модель видит описание и, если решит, что оно подходит, вернёт не текст, а
  структуру `tool_calls`.
- `tools=[schema]` — передаём схему в запрос.
- Ключевой момент: **функция НЕ вызвана**. В ответе лежит только «просьба»:
  имя `count_places` и аргументы строкой `{"kind": "pharmacy"}`. Выполняет вызов
  ваш код — этого ещё нет.
- `answer.usage` — счётчик токенов: сколько ушло на вход (промпт+схемы) и на выход.

**Результат в консоли:** модель попросила позвать `count_places {"kind": "pharmacy"}`,
токенов: 125 вход, 28 выход.

**Вопросы преподавателя и ответы:**
- *Почему вызов — это строка, а не настоящий вызов функции?* Потому что модель
  генерирует текст. «Вызов инструмента» — участок ответа: имя функции и JSON
  аргументов. Безопасность: модель не может выполнить произвольный код, только
  попросить.
- *Почему токенов входа больше?* На вход идут системный текст, вопрос, описание
  схемы; на выход — только кусок с вызовом. Вход всегда дешевле за токен, но его
  больше.
- *Сколько таких запросов нужно на агента?* Минимум два: первый — просит вызов,
  второй (с результатом вызова) — отвечает. Обычно больше, если вызовов несколько.

## Задача 1. Первый агент

**Что было задачей.** Превратить три функции из `sdk_tasks.py`
(`count_places`, `find_places`, `top_brands`) в инструменты агента и получить ответ
на вопрос. Подвох: у `top_brands` **нет докстроки** — без описания модель в неё
промахнётся, ошибки не будет, просто тишина. Нужно:
1. заполнить `instructions` агента (чем он занимается и чего не делать);
2. дать описание функции без докстроки через `description_override`.

**Что сделано:**

```python
agent = Agent(
    name="Городская справочная",
    instructions=(
        "Отвечаешь на вопросы о Ростове-на-Дону только по базе мест города, "
        "пользуясь инструментами. Все числа бери из ответов инструментов, "
        "не выдумывай их. Если данных в базе нет — прямо скажи об этом."
    ),
    tools=[function_tool(count_places),
           function_tool(find_places),
           function_tool(top_brands, description_override=(
               "Возвращает таблицу самых частых брендов мест заданного вида: "
               "бренд и количество. Зови на вопросы про сети и бренды "
               "(«какие сети представлены в городе», «самый частый бренд»). "
               "Не зови для списков конкретных мест, адресов и расстояний — "
               "для этого есть find_places."))])

result = await Runner.run(agent, "Сколько в Ростове круглосуточных аптек?")
print(result.final_output)
```

**Разбор «для чайника»:**
- `Agent` — объект агента: имя, инструкции (это системное сообщение — текст,
  который SDK кладёт **первым** в каждый запрос к модели, перед вопросом
  пользователя), список инструментов.
- `instructions` отвечает на три вопроса модели: что я делаю, чем пользуюсь, чего
  не делаю. Без этого модель начнёт отвечать **по памяти** про Ростов («их там
  примерно 300») вместо вызова инструмента. Формулировка «все числа бери из
  ответов инструментов, не выдумывай» — прямой запрет галлюцинаций.
- `function_tool(func)` — обёртка: имя функции → имя инструмента, аннотации типов
  → схема параметров, докстрока → описание инструмента и описания полей (секция
  `Args:`). То есть докстрока — это не комментарий для коллег, а **интерфейс для
  модели**.
- `description_override="..."` — способ задать описание, если докстроки нет
  (или перезаписать её). Описание по шаблону: **что возвращает → когда звать →
  когда НЕ звать (и что звать вместо)**.
- `Runner.run(agent, вопрос)` — фреймворк сам крутит цикл «модель → вызов →
  результат → модель», пока не получит финальный текст.

**Результат:** «В Ростове-на-Дону 19 круглосуточных аптек.»
**Проверка:** `check_first_agent` — ✓ у всех инструментов есть описание (пустое
описание = «—» = провал), ✓ в ответе есть верное число 19 (оно же посчитано из
базы: `SELECT COUNT(*) … kind='pharmacy' AND is_24_7=1`). **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему пустая докстрока — это ошибка, а не warning?* Модель видит только
  описания. Нет описания — модель не знает, что инструмент существует и за что он,
  и просто не зовёт его. Ошибки нет, но результат плохой — поэтому это и считается
  типичной ошибкой.
- *Что важнее: инструкции или описания инструментов?* Оба слоя: инструкции —
  политика всего агента («отвечай только по базе»), описания — выбор конкретного
  инструмента. Задание 4 вообще меняет **только** описания и показывает, что этого
  достаточно, чтобы изменить поведение.
- *Где взять 19?* Из базы: 19 круглосуточных аптек (`is_24_7=1`). Проверка берёт
  число из SQLite, а не из головы.

## Задача 2. Цепочка: результат одного инструмента — вход следующего

**Что было задачей.** Вопрос «где ближайшая аптека и до скольки работает» не
решается одним вызовом: нужна цепочка **адрес → координаты → id ближайшей → часы
работы**. В `ДАНО` две функции специально возвращают «неправильно» — в них нет
координат и id, и цепочка обрывается. Нужно починить два `return` и написать
`instructions`.

**Что сделано:**

```python
@function_tool
def geocode(street: str, housenumber: str) -> str:
    """Координаты дома по адресу."""
    place = address_point(street, housenumber)
    if place is None:
        return "такого адреса в базе нет"
    # координаты в строке — из них следующий инструмент и будет работать
    return (f"дом найден: {place['street']}, {place['housenumber']} "
            f"lat={place['lat']}, lon={place['lon']}")

@function_tool
def nearest_place(lat: float, lon: float, kind: str) -> str:
    """Ближайшее к точке место заданного вида: pharmacy, cafe, outpost."""
    found = nearest(lat, lon, kind, 1)
    if not found:
        return f"мест вида {kind} в базе нет"
    best = found[0]
    return f"id={best['id']} {best['name'] or 'без названия'} — {best['distance_m']} м"

@function_tool
def place_details(place_id: int) -> str:
    """Карточка места по его идентификатору: часы работы и телефон."""
    card = details(place_id)
    return f"{card['name']} · часы: {card['opening_hours']} · телефон: {card['phone']}"

agent = Agent(name="Городской помощник",
              instructions=(
                  "Иди строго по порядку: "
                  "1) geocode — превращает адрес в координаты; "
                  "2) nearest_place — ищет ближайшее место по координатам из ответа geocode; "
                  "3) place_details — карточка места по id из ответа nearest_place. "
                  "Координаты и id бери из текста ответов инструментов, не выдумывай их сам."
              ),
              tools=[geocode, nearest_place, place_details])
```

**Разбор «для чайника»:**
- Главный принцип: **между инструментами нет проводов**. Единственное, что
  доходит от первого инструмента до второго, — **текст его результата**, который
  модель прочитала. Поэтому формат результата — такой же интерфейс, как и
  описание: если в строке нет координат, взять их неоткуда.
- `lat=…, lon=…` в ответе `geocode` — чтобы модель могла **прочитать** числа и
  подставить в `nearest_place`. Без них цепочка обрывается на шаге 1 (так и
  происходило при первом запуске — об этом предупреждало `ДАНО`).
- `id=…` в ответе `nearest_place` — модель должна вытащить его и передать в
  `place_details(place_id=…)`.
- `instructions` задаёт **порядок**: сначала адрес в координаты, потом ближайшее,
  потом карточка. И прямой запрет: координаты и id — из ответов инструментов, а не
  из головы (иначе модель сгенерирует правдоподобные, но выдуманные координаты).
- `@function_tool` — декоратор, сокращение от `function_tool(...)` той же задачи.

**Результат:** агент ответил «Ближайшая аптека … „Лаки Фарма“ — 123 метра, часы
08:00–21:00…», а в журнале видно ровно три вызова: `address_point` (с координатами
47.27917, 39.74933) → `nearest` (с этими же координатами) → `details` (с id
найденной аптеки).
**Проверка:** ✓ три вызова в нужном порядке, ✓ в поиск ушли координаты дома
(а не выдуманные), ✓ карточка именно той аптеки, что нашли (id 1728), ✓ в ответе
есть часы `08:00-21:00`. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему нельзя «просто пробросить объект»?* Можно, если инструменты вызывает твой
  код (так и делает `Runner` — но данных между инструментами он не переносит).
  Переносит их только модель, читающая текст. Это принципиальное ограничение
  архитектуры «модель в цикле».
- *А если модель вставит не те координаты?* Проверка это ловит: она сверяет
  координаты в вызове `nearest` с координатами из базы (допуск 0.001°).
- *Почему возвращается строка, а не dict?* Потому что модель читает текст. Строка
  с явными `lat=…`/`id=…` надёжнее JSON в плане «глазами видно» — и это дешевле по
  токенам.

## Задача 3. Запрос объектом

**Что было задачей.** Вместо плоских аргументов (`kind`, `street`, `only_24_7` —
каждый отдельно) собрать **один объект-запрос** через pydantic-модель `PlaceQuery`
и передать его инструменту. Показать, что даёт схема: поле с перечнем допустимых
значений нельзя «выдумать». Нужно: заменить `kind: str` на `kind: Kind | None`
(готовое перечисление из `sdk_tasks`), заполнить `description` каждому полю.
Нужно 5 верных запросов из 6.

**Что сделано:**

```python
from pydantic import BaseModel, Field, model_validator

class PlaceQuery(BaseModel):
    """Запрос к базе мест города."""
    kind: Kind | None = Field(None, description="вид места из закрытого перечня: pharmacy, cafe, ... — ровно как в вопросе, латиницей")
    street: str | None = Field(None, description="часть названия улицы для фильтра, кириллицей, например Пушкин; None — если улица не упомянута")
    brand: str | None = Field(None, description="сеть/бренд, например Ozon; писать точно так, как в вопросе; None — если бренд не упомянут")
    only_24_7: bool = Field(False, description="True только когда в вопросе прямо сказано «круглосуточно»; иначе False")
    limit: int = Field(5, description="сколько строк вернуть")

    @model_validator(mode="before")
    @classmethod
    def _decode_if_string(cls, data):
        # Наш провайдер ломает $ref-схемы: вместо объекта модель присылает JSON-строку
        if isinstance(data, str):
            try:
                return json.loads(data)
            except ValueError:
                return data
        return data

@function_tool
def search_places(q: PlaceQuery) -> str:
    """Поиск мест города по запросу."""
    return run_query(q)
```

**Разбор «для чайника»:**
- `PlaceQuery` — pydantic-модель. Фреймворк превращает её в JSON-схему для модели:
  поля, типы, описания. Модель обязана собрать объект по этой схеме.
- `Kind | None` — перечисление (Enum) из 13 видов мест. **Схема гарантирует то, что
  описанием нельзя гарантировать**: модель не сможет прислать `kind="аптека"`,
  декодирование ограничено списком. Описанием можно попросить, схемой — запретить.
- `Field(None, description=...)` — описание поля; из него SDK собирает описания
  полей схемы (в формате `Args:` у докстроки — тот же эффект, второй способ).
  В описании `only_24_7` прямо сказано, когда ставить `True` — это и есть
  «описание с границами применимости».
- `@model_validator(mode="before")` — костыль под нашего провайдера: иногда модель
  присылает не объект, а JSON-строку (сломанные $ref-схемы у посредника).
  Валидатор раскодирует строку; дальше поля всё равно проверяются по типам, так что
  защита `Kind` остаётся.
- `run_query(q)` — «дано», собирает SQL по полям объекта: `WHERE kind=? AND street
  LIKE ? AND brand LIKE ? AND is_24_7=1 LIMIT ?`.

**Результат:** все 6 вопросов собраны верно, например:
- «Какие аптеки работают круглосуточно?» → `{kind: pharmacy, only_24_7: True}`
- «Покажи пункты выдачи сети Ozon» → `{kind: outpost, brand: Ozon}`
- «Школы на улице Доватора» → `{kind: school, street: Доватор}`
**Проверка:** ✓ 6 из 6 (нужно 5). **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Чем объект-запрос лучше плоских аргументов?* Одной схемой описывается вся
  область поиска; поля можно валидовать целиком; добавить поле = добавить поле
  модели, а не тянуть новый аргумент через все вызовы.
- *Зачем `None` у полей?* Опциональность: в вопросе про круглосуточные аптеки улицы
  нет → `street=None`, и SQL не добавляет фильтр. Модель не обязана угадывать
  «необязательные» значения.
- *Почему описания полей важнее, чем кажется?* Потому что модель видит именно их.
  «True только когда прямо сказано „круглосуточно“» — прямая инструкция против
  «поставить True на всякий случай».

## Задача 4. Описание решает

**Что было задачей.** Два похожих инструмента: список мест (`find_places`) и
ближайшее к точке (`nearest_place`). Восемь вопросов, у каждого известен правильный
инструмент. Менять можно **только докстроки** (код — нельзя). Метрика — доля
верного первого выбора; нужно ≥ 0.9.

**Что сделано:** каждому инструменту — докстрока по шаблону:

```python
@function_tool
def find_places(kind: str, street: str | None = None) -> str:
    """Список мест города заданного вида, при желании — фильтр по улице.

    Зови, когда нужен перечень: «какие аптеки есть», «покажи кафе на улице»...

    Не зови, если вопрос про близость к точке с координатами: «ближе всего»,
    «ближайший», «сколько метров до» ... — для этого есть nearest_place.

    Возвращает табличку: id, название, адрес, часы работы.

    Args:
        kind: вид места латиницей: pharmacy, cafe, supermarket, fuel и т.д.
        street: часть названия улицы; None — поиск по всему городу.
    """
    return db_find(kind, street)
```
и симметрично для `nearest_place` (там наоборот: «Не зови для перечней мест по
городу ... — это find_places»).

**Разбор «для чайника»:**
- Модель выбирает между инструментами **исключительно по описаниям** — другого
  у неё нет. Описание в одно слово = выбор вслепую.
- Шаблон описания (им он и выиграл): **что делает → когда звать → когда НЕ звать
  и что звать вместо → что вернёт → Args**. Фраза «для этого есть другой
  инструмент» — самый сильный приём: она разводит похожие инструменты явно.
- Секция `Args:` — так фреймворк берёт описания полей схемы.

**Результат:** `доля верного выбора: 1.0` (8 из 8).
**Проверка:** ✓ 1.0 ≥ 0.9. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему метрика именно первый выбор?* Потому что меряем качество описания, а не
  удачу: если первый вызов верен, модель поняла инструменты; если нет — исправится
  она или нет, описания не сработали.
- *Какие слова разводят инструменты?* Лексика вопроса: «какие/покажи/перечисли» —
  перечень; «ближе всего/метров до/координаты» — близость. Их нужно перечислить в
  описании.
- *А если описать красиво, но для человека?* Не сработает: нужны единицы
  («метры»), границы («None — если улицы нет»), примеры формулировок. Красота ≠
  полнота.

## Задача 5. Что нельзя выбрасывать (сессия)

**Что было задачей.** Три вопроса диалога, третий осмыслен только вместе с первым:
«А сколько из них круглосуточных?» — из каких? Модель не помнит ничего между
запусками: память — это **история, которую отправляешь ты**. Нужно провести диалог
дважды: без памяти и с `SQLiteSession`.

**Что сделано:**

```python
without_memory = []
for question in DIALOG:
    without_memory.append((await Runner.run(agent, question)).final_output)  # каждый раз с чистого листа

session = SQLiteSession("rostov-city-dialog")
with_memory = []
for question in DIALOG:
    with_memory.append((await Runner.run(agent, question, session=session)).final_output)
```

**Разбор «для чайника»:**
- У модели нет состояния между запросами. «Память чата» — это иллюзия клиента: на
  каждый запрос уходит вся история сообщений заново.
- Без сессии каждый вопрос — отдельный чат. На «сколько из них?» модель не знает,
  про что «них», и либо галлюцинирует, либо переспрашивает.
- `SQLiteSession` хранит историю в файле SQLite и передаёт её в запуск: SDK сам
  подставляет прошлые реплики в сообщения.
- Важно: сессия переживает перезапуски ноутбука — «имя разговора» это и есть ключ.

**Результат (из вывода):**
- без памяти: «Уточните, пожалуйста, какие именно места вы имеете в виду…» —
  модель честно не поняла контекст;
- с памятью: «Из 330 аптек Ростова 19 работают круглосуточно.» — верно и по делу.

**Проверка:** ✓ с сессией последний ответ верный (19), ✓ без сессии ответ «не про
аптеки» — так и должно быть. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Что именно хранит сессия?* Список прошлых сообщений (роли и тексты). SDK
  подмешивает их в `messages` при следующем запуске.
- *Почему ответ без памяти — не баг?* Это ожидаемое поведение: оно и демонстрирует,
  что памяти без сессии нет. Проверка специально требует, чтобы он был «не про
  аптеки».
- *Сколько это стоит по токенам?* История растёт с каждым ходом и попадает в
  входные токены — память = деньги. Отсюда вытекает смысл задачи 6.

## Задача 6. Предохранитель и цена

**Что было задачей.** Упрямый инструмент, который на любой вызов просит «уточните
фильтр»: агент зовёт снова, снова, снова — пока кто-то не остановит. Нужно поставить
**лимит шагов** и посчитать **цену** нормального прогона.

**Что сделано:**

```python
turns = 2                        # минимальный лимит: круг виден сразу, деньги не утекают
try:
    await Runner.run(stubborn,
                     "Найди кафе в городе. Не переспрашивай: вызывай инструмент поиска ...",
                     max_turns=turns)
except MaxTurnsExceeded:
    stopped = True
    print("упёрлись в лимит шагов")

ok = await Runner.run(normal, "Сколько в Ростове аптек?", max_turns=3)
price = cost_rub(ok.context_wrapper.usage)
print("прогон стоил", price, "₽")
```

**Разбор «для чайника»:**
- `max_turns` — предохранитель: SDK прекращает прогон и бросает
  `MaxTurnsExceeded`. Без него цикл был бы бесконечным, а платить за него — тебе.
- `turns=2` выбрано специально маленьким: круг «видно» уже на втором шаге, а
  деньги не успевают утечь. В реальном агенте лимит ставят по-человечески (например
  8), но принцип тот же.
- `ok.context_wrapper.usage` — агрегированный счётчик токенов прогона
  (`input_tokens`/`output_tokens`).
- `cost_rub` (из `sdk_tasks`): `вход/1e6 × 30 + выход/1e6 × 120` — цена по тарифу.

**Результат:** «упёрлись в лимит шагов», «прогон стоил 0.0275 ₽».
**Проверка:** ✓ прогон остановлен предохранителем, ✓ лимит разумный (2 в диапазоне
2–8), ✓ цена посчитана. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему именно лимит шагов, а не таймаут?* Таймаут ловит зависание, лимит —
  логическую петлю. Петля враг №1: она не зависает, она вежливо крутится и копит
  счёт.
- *Почему цена входа и выхода разная?* Выходные токены считать дороже (они
  генерируются последовательно); тарифы провайдеров такие: 30 против 120 ₽/млн.
- *Что если лимит слишком маленький?* Честный агент не успеет ответить — будут
  ложные отказы. Too big = деньги. Поэтому лимит подбирают и смотрят на статусы.

## Задача 7. Форма, при которой нельзя соврать

**Что было задачей.** Модель отдаёт отчёт объектом. Схема гарантирует **форму**, но
не **правду**: вот отчёт со спросом 999, нулём метров до конкурента и нулём
осмотренных кварталов. Нужно поставить ограничения (`Field(...)`), при которых
подложный отчёт не пройдёт, а настоящий — пройдёт.

**Что сделано:**

```python
class Place(BaseModel):
    lat: float
    lon: float
    demand: int = Field(..., ge=1, le=100)          # спрос: 1..100, «999» невозможно
    competitor_distance_m: int = Field(..., ge=1)   # до конкурента не бывает 0 метров
    why: str

class Report(BaseModel):
    places: list[Place]
    checked_cells: int = Field(..., ge=1)           # осмотрен хотя бы один квартал
```

**Разбор «для чайника»:**
- `Field(...)` — многоточие означает «поле обязательное» (язык pydantic, не наша
  заготовка); ограничения пишутся **после запятой**: `ge=1` (>=), `le=100` (<=).
- Смысл: **схема — это фильтр правдоподобия**. Спрос 999 физически не проходит
  валидацию, значит модель не сможет прислать отчёт со спросом 999.
- Ловушка: перекрутишь (`ge=0, le=10^9`) — отсечёшь подложный отчёт? Нет, но и
  смысл границ исчезнет. Проверка гоняет **и подложный, и настоящий** отчёт, плюс
  портит каждое поле отдельно — чтобы задачу не закрыть одной строчкой.

**Проверка:** ✓ подложный отчёт целиком не проходит, ✓ спрос 999 не проходит, ✓ 0
метров не проходит, ✓ 0 кварталов не проходит, ✓ настоящий отчёт (demand 34,
competitor 410, checked_cells 8) проходит. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Схема гарантирует правду?* Нет — только форму. Правду проверяет сверка с данными
  (это продолжится в задании: ground truth из базы).
- *Почему ge=1, а не ge=0 для расстояния?* Ноль метров до конкурента означал бы,
  что точка стоит ровно на конкуренте — для «нового места» это нелепо; минимум 1 м
  отсекает нулевой мусор, не мешая честным данным (410 м).
- *Что если честный отчёт имеет demand 250?* Тогда границы надо обосновать иначе —
  границы должны следовать из домена (в базе спрос — это число меток в радиусе,
  разумный порядок — единицы/десятки), а не из желания пропустить конкретный пример.

## Задача 8. Гардрейл

**Что было задачей.** Модель послушно напишет стихотворение про Ростов — за твои
деньги. Нужно отсекать посторонние вопросы **до** того, как за них заплатят. Условие
пишется обычным питоном, модель для проверки не нужна.

**Что сделано:**

```python
@input_guardrail(run_in_parallel=False)
async def city_only(ctx, agent, text):
    t = str(text).lower()
    off_topic = any(word in t for word in ("стих", "переведи", "уравнен", "анекдот"))
    return GuardrailFunctionOutput(output_info={"вопрос": text}, tripwire_triggered=off_topic)

agent = Agent(name="Справочная", instructions="Отвечай по базе города.",
              tools=[function_tool(count_places)], input_guardrails=[city_only])

for question in asked:
    try:
        await Runner.run(agent, question)
        blocked.append(False)
    except InputGuardrailTripwireTriggered:
        blocked.append(True)
```

**Разбор «для чайника»:**
- Гардрейл — функция, которую зовёт SDK. Ей передают `ctx` (контекст), `agent`,
  `text` (вопрос пользователя); возвращает она `GuardrailFunctionOutput`, где
  решает поле `tripwire_triggered`: `True` — «стоп».
- На `True` SDK прерывает прогон исключением `InputGuardrailTripwireTriggered` —
  его ловит `try/except`. Проверка идёт **до** работы агента → посторонний запрос
  не стоит ни копейки.
- `run_in_parallel=False` — по умолчанию гардрейл идёт параллельно агенту (старт
  вместе, отмена при срабатывании). С `False` проверка строго предшествует работе —
  экономнее и предсказуемее.
- `str(text).lower()` — текст бывает не строкой, приводим принудительно; регистр
  не важен («Стихи»/«стихи»).
- Условие — «жадное» наоборот: ключевые слова (стих, переведи, уравнен, анекдот),
  а НЕ «нет слова Ростов» — иначе зарубишь и нормальные вопросы (проверка это
  отдельно ловит).

**Результат:** все 6 нормальных пропущены, все 4 посторонних отсечены.
**Проверка:** ✓ все посторонние отсечены, ✓ нормальные прошли. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему не модель для проверки?* Потому что тогда за каждый фильтр платишь
  прогоном и получаешь ненадёжность. Детерминированный Python — быстро и бесплатно.
- *Чем гардрейл отличается от инструкции «не отвечай на постороннее»?*
  Инструкция — пожелание, гардрейл — код: модель его не обойдёт.
- *А если пользователь напишет «вирш про Ростов»?* Ключевые слова не поймают —
  это компромисс простого фильтра; в проде комбинируют правила и классификатор.

## Задача 9. Триаж (передача между агентами)

**Что было задачей.** Два готовых агента: `Reference` (факты по базе) и `Analyst`
(выбор места под точку). Вопросы приходят вперемешку. Нужен третий агент, который
**сам не отвечает никогда**, а только раздаёт работу через `handoffs`.

**Что сделано:**

```python
triage = Agent(
    name="Триаж",
    instructions=(
        "Ты — только маршрутизатор. Сам НИКОГДА не отвечай на вопрос пользователя: "
        "всегда сразу передавай его через передачу (handoff) нужному агенту.\n"
        "Reference — фактические вопросы о городе: «сколько», «какие», перечни мест, "
        "сети, адреса, часы работы. Примеры: «Сколько в городе круглосуточных аптек?», ... \n"
        "Analyst — выбор и оценка места под новую точку: «где открыть», «спрос», "
        "«конкуренция», «стоит ли ставить», сравнение кварталов. Примеры: ... \n"
        "Свой ответ не формулируй — выбери агента и передай вопрос ему."
    ),
    handoffs=[reference, analyst])

routed = []
for question, _ in MIXED:
    routed.append((await Runner.run(triage, question)).last_agent.name)
```

**Разбор «для чайника»:**
- `handoffs` — передача «выполни это за меня». SDK реализует её как скрытые
  инструменты `transfer_to_...`; когда модель такой вызывает, эстафету принимает
  целевой агент, и его `last_agent.name` мы и видим.
- Отсюда требование: имена агентов латиницей (`Reference`, `Analyst`) — имя
  инструмента в схеме должно быть из букв/цифров/подчёркиваний.
- Пустая инструкция триажа = баг: агент начинает отвечать сам. Поэтому в ней три
  обязательных куска: (1) «сам никогда не отвечай», (2) признак вопросов
  `Reference` + примеры, (3) признак вопросов `Analyst` + примеры.

**Результат:** `['Reference', 'Analyst', 'Reference', 'Analyst', 'Reference', 'Analyst']`.
**Проверка:** ✓ 6 из 6 ушли по адресу. **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Handoffs или один агент со всеми инструментами?* Разные инструменты и роли
  смешивать вредно: описания мешают друг другу (см. задачу 4), а маршрутизатор
  дешёвый и чистый.
- *Чем `last_agent.name` отличается от последнего вызванного инструмента?*
  `last_agent` — агент, который финально отвечал; имя и есть факт передачи.
- *Почему примеры фраз в инструкции?* Потому что границы решаются по лексике;
  примеры — самый дешёвый способ задать её модели.

## Задача 10. Три адреса (отчёт объектом + сверка с базой)

**Что было задачей.** Финал: агент отдаёт отчёт объектом (`output_type=Answer`) с
координатами, спросом и расстоянием до конкурента. Схема обещает форму, но не
правду — поэтому **первое место отчёта надо пересчитать самой по базе** и сравнить.
Сойдётся или нет — заранее неизвестно: это и есть смысл сверки.

**Что сделано:**

```python
class Spot(BaseModel):
    lat: float
    lon: float
    demand: int
    competitor_distance_m: int
    why: str

class Answer(BaseModel):
    places: list[Spot]
    checked_cells: int

agent = Agent(name="Аналитик",
              instructions="Ищи места по базе города: сначала посмотри кварталы с наибольшим "
                           "спросом, потом проверь по ним спрос и конкурентов. Все числа в "
                           "отчёте бери из ответов инструментов.",
              tools=[function_tool(best_cells), function_tool(demand_in_cell),
                     function_tool(competitors_near)],
              output_type=Answer)

report = (await Runner.run(agent, LETTER)).final_output

# сверка
first = report.places[0]
hand_demand = demand_in_cell(first.lat, first.lon)        # спрос вокруг точки — по базе
hand_competitors = competitors_near(first.lat, first.lon) # конкуренты — тоже по базе
```

**Разбор «для чайника»:**
- `output_type=Answer` — SDK требует от модели ответ по схеме класса и парсит его
  в объект: дальше `report.places[0].lat`, а не «резать текст».
- `LETTER` — письмо «директора»: три адреса, по каждому координаты, спрос, расстояние
  до конкурента.
- Ручная сверка: мои `hand_demand`/`hand_competitors` считаются **теми же**
  функциями по базе — это и есть «пересчитать самой».

**Результат (из вывода):**
- агент: `100 спроса, 1000 м до конкурента`;
- расчёт: `0 спроса, 0 конкурентов в радиусе 500 м`.
- вердикт: **расхождение 100 vs 0 — не ошибка твоего кода, это и есть ответ**:
  числа в отчёте модели не подтвердились данными.
**Проверка:** ✓ спрос посчитан верно (0 = 0), ✓ конкуренты посчитаны верно
(0 = 0). **ЗАДАЧА ЗАЧТЕНА.**

**Вопросы преподавателя и ответы:**
- *Почему не засчитали отчёт агента?* Потому что пункт задания — проверить
  **свой** ручной пересчёт по базе; отчёт модели печатается рядом для сравнения.
- *Почему агент получил 100 и 1000?* Подозрительно «круглые» числа — признак
  того, что модель иногда подставляет правдоподобное вместо измеренного. Ровно
  поэтому нужны сверка с данными и ground truth (это продолжение темы задачи 7).
- *Что брать на прод?* Не доверять отчёту агента: либо пересчитывать критичные
  числа кодом (как здесь), либо отправлять отчёт второму агенту-судье.

- **short**: одна фраза («Сколько в городе мест такого вида») и однословные

- **full**: что делает → когда звать → **когда НЕ звать и что звать вместо** →
  что вернёт и в каких единицах → пример вызова; в полях — перечень
  допустимых значений `kind` **латиницей** и границы (`only_24_7: True только
  когда прямо спрашивают про круглосуточные`).

## `agent.py` — цикл без фреймворка (то, за что отвечают 30 баллов)

Псевдокод:

```python
messages = [system_prompt, вопрос]
для step в 1..max_steps(8):
    ответ = client.chat.completions.create(model, messages, tools=схемы)  # с ретраем ×3
    прибавить ответ.usage → input_tokens, output_tokens
    если у ответа НЕТ tool_calls:        → статус "ok", финальный текст, выход
    для каждого вызова:
        результат, запись = _execute(name, arguments)   # ошибки → строка
        messages.append({role: "tool", content: результат})
иначе (лимит исчерпан): статус "max_steps"
цена = вход/1e6×30 + выход/1e6×120
записать прогон одной строкой в runs/*.jsonl
```

Что тут сделано руками и зачем:

1. **Лимит шагов `max_steps=8`.** Исчерпан — прогон закрыт статусом `max_steps`,
   без падения и без бесконечной петли.
2. **Ошибки как наблюдения** — три вида, все превращаются в текст для модели:
   - нет инструмента → «ошибка: инструмента X нет; доступны: …»;
   - битый JSON аргументов → в наблюдение попадают **сами аргументы модели** и
     пример корректного вызова;
   - исключение внутри функции → «ошибка при выполнении …; поправь и вызови снова».
   Цикл не падает никогда — модель получает шанс исправиться (это пункт из
   «типичных ошибок прошлых лет»).
3. **Починка аргументов** (`_parse_args`), потому что провайдер реальной лаборатории
   ломал JSON двумя способами:
   - без кавычек: `{"street": Пушкин}` → чинится до `{"street": "Пушкин"}` (голые
     ключи/значения, одинарные кавычки, `True/None` → `true/null`);
   - **обрезка посередине**: `{"kind": "cafe", "street": ` — конец отсутствует.
     Сначала пробуем закрыть незакрытые кавычки и скобки; если не вышло — достаём
     полный вызов из текста ответа модели (модель продублировала его в `content`
     в виде меток `<parameter=имя>значение` + закрывающая метка). Факт починки
     пишется в журнал флагом `repaired`.
4. **Ретрай запроса** (3 попытки с паузой 2/4 с) — сетевой сбой или rate limit не
   стоит прогона. Итог: **0 ошибок среды за 90 прогонов**.
5. **Счёт токенов и денег** из `usage` каждого шага; тариф 30/120 ₽/млн (как в
   практике, переопределяется `PRICE_IN`/`PRICE_OUT` в `.env`).
6. **JSONL-журнал**: одна строка на прогон — вопрос, статус, шаги, каждый вызов
   (имя, аргументы, результат, ошибка, починен ли), токены, цена, вердикты
   `passed`/`tool_ok`. Это «чёрный ящик» для разбора ошибок.

## `check.py` — как считаются метрики (25 баллов)

Команды:
```bash
uv run python check.py --n 3           # 10 задач × 3, вариант full
uv run python check.py --ab --n 3      # short и full по 3 прогона
```

- **pass@1** = (число прогонов, где судья сказал «верно») / (всего прогонов).
  При n=3 это 30 прогонов.
- **pass^3** = (число задач, где **все три** прогона успешны) / 10.
- **tool_ok (метрика A/B)** = первый вызов прогона совпал с ожидаемым инструментом
  И аргументами (сверка с допусками).
- **Интервал Вильсона 95%** — доверительный интервал для доли k/n. Зачем: 3
  прогона — мало, голая «96%» ничего не значит. Вильсон показывает, в каком
  диапазоне настоящая доля с вероятностью 95%. Если интервалы двух вариантов
  **не перекрываются** — разница значима.
  Формула: центр `(p + z²/2n) / (1 + z²/n)` плюс-минус полуширина
  `z·√(p(1−p)/n + z²/4n²) / (1 + z²/n)`, при z = 1.96.
- **Цена прогона** = `вход/1e6 × 30 + выход/1e6 × 120`.

### A/B описаний (`--ab --n 3`)

| Показатель | short | full | Δ |
|---|---|---|---|
| **Точность первого вызова** | 6.7% (2/30), Вильсон [0.02, 0.21] | **100% (30/30)**, Вильсон [0.89, 1.00] | **+93.3 п.п.** |
| pass@1 | 93.3% | 100% | +6.7 п.п. |
| Токены/прогон | 4458 | 4482 | +24 (+0.5%) |
| Деньги/прогон | 0.1669 ₽ | 0.1516 ₽ | −0.0153 ₽ |
| Шаги | 3.3 | 2.1 | −1.2 |

**Ответ числом: полные описания стоили +24 токена на прогон (+0.5%) и дали
+93.3 п.п. точности первого вызова; интервалы Вильсона не перекрываются —
окупились. В деньгах full дешевле (−0.0153 ₽/прогон).**

**Почему так:**
- short говорит про `kind` только «вид места» → модель пишет `kind="аптека"`
  (по-русски, как в вопросе) → база отвечает «вида нет» → лишний шаг
  самокоррекции. 28 из 30 прогонов начали с неверного аргумента — метрика
  первого вызова и рухнула.
- full перечисляет значения **латиницей** и границы → правильный вызов с первого
  раза, 30/30.
- Ответ в итоге верный почти у обоих (93% против 100%) — модель учится на ошибке.
  Но «починка» стоит шагов: 3.3 против 2.1, и эти лишние круги дороже, чем
  сэкономленные короткие схемы. Отсюда минус у short по деньгам.
- Вывод: **описание инструмента — это инвестиция в первый вызов, которая
  окупается на следующем же шаге; короткое описание бесплатно только на бумаге.**

### Три разбора неудачных траекторий

1. **Не те аргументы → ложное «готово»** (провал pass, short/`brands_outpost`):
   «Какие сети пунктов выдачи?» → `top_brands(kind="пункт выдачи")` → ошибка
   «вида нет; есть: …» → модель вместо `outpost` подставляет `post_office` и
   уверенно выдаёт цифры Почты России вместо Ozon. Корень — описание не называло
   допустимые значения.
2. **Не тот инструмент** (провал метрики первого вызова, short/`find_outposts`):
   «Покажи пункты выдачи» (ждём `find_places`), а первый вызов — `count_places` +
   тот же неверный `kind`. На шаге 2 модель исправилась и ответила верно, но
   лишний раунд оплачен.
3. **Зацикливание (почти петля)** (short/`find_outposts`, 6 шагов): перебор
   «пункт выдачи заказа → post_office → счётчик → outpost», потом осмысленная
   работа. Сошёлся лишь потому, что лимит 8; при `max_steps=4` прогон был бы
   потерян. Это ровно «ошибка в фильтре → бесконечный цикл» из типичных ошибок —
   спасает только предохранитель, а корень чинится описанием.

Ошибок среды (обрывов API) за 90 прогонов — ноль.

### Как типичные ошибки прошлых лет закрыты

| Типичная ошибка | Как закрыто у нас |
|---|---|
| исключение инструмента роняет цикл | любая ошибка → строка-наблюдение «ошибка: …», цикл продолжается (тесты это проверяют) |

| описание написано для человека | full: единицы, границы применимости, примеры, «когда НЕ звать» — и это доказано A/B (+93.3 п.п.) |

## Возможные вопросы преподавателя по заданию — и ответы

- **Почему свой цикл, а SDK уже есть?** Задание требует «цикл без фреймворка»: под
  капотом `Runner` ровно этот код. Написав его руками, видишь просьюбу модели
  (это не вызов), наблюдение, лимит, счёт денег — и понимаешь, что фреймворк
  скрывает.
- **Откуда ground truth?** Из `poi.sqlite` прямым SQL, без модели. Иначе
  сравниваешь модель с моделью.
- **Что именно меряет A/B?** Долю (задача, прогон), где **первый** вызов — верный
  инструмент и верные аргументы. Это чистое качество описаний: ответ можно
  «вылечить» самокоррекцией, а первый выбор — нет.
- **Почему Вильсон, а не просто проценты?** n=30 маленькое; Вильсон даёт честный
  диапазон. Перекрытие/неперекрытие интервалов — критерий значимости разницы.
- **Сколько стоило?** ~15 ₽ на все 90 финальных прогонов (30+30+30), тариф
  30/120 ₽/млн.
- **Почему pass@1 = 100%?** Маленькая выборка и сильная модель на коротких
  вопросах; в отчёте оговорено. Главный результат — не 100%, а A/B-разница.
- **Что было сложно?** Провайдер обрезал аргументы и писал JSON без кавычек;
  обычный `json.loads` это не чинит. Решение: многоступенчатая починка +
  восстановление из текстового дубля вызова; случаи видны в журнале флагом
  `repaired` (6–12 на 30 прогонов).
- **Почему инструменты возвращают ошибку строкой?** Чтобы модель получала шанс
  исправиться: исключение = смерть цикла, строка = обратная связь.
- **Что если менять не описания, а промпт?** A/B изолирован: системный промпт один
  и тот же в обоих вариантах, меняются ровно тексты схем — значит, разница
  обусловлена именно описаниями.
- **Почему две задачи с близкими вопросами (кафе/аптеки на улице)?** Чтобы метрика
  не держалась на одном типе: счётчики, списки, бренды, близость, цепочка —
  разные пути выбора инструмента.

## Как запустить и сдать

На чистой машине (Python 3.12, `uv`, ключ OpenAI-совместимого сервиса):

```bash
git clone https://github.com/iprastas/ai_course_mmcs_st.git
cd ai_course_mmcs_st
uv sync
cp .env.example .env      # вписать OPENAI_API_KEY, OPENAI_BASE_URL, MODEL
uv run pytest             # 12 тестов, без API
uv run python check.py --n 3
uv run python check.py --ab --n 3
```

- Отчёт: `week2/assignment/report.md`.
- Журналы прогонов: `week2/assignment/runs/*.jsonl`.
- Ключ в `.env` лежит в `.gitignore` и в репозиторий не попадает.
- Стоимость повторного прогона всей схемы: порядка 15 ₽.
