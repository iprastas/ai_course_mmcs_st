# Задание 1: отчёт

Индивидуальное задание недели 2. Всё лежит в `week2/assignment/`, запускается из корня
репозитория командой `uv run python check.py --n 3` (переходник `check.py` в корне).
Модель: `xiaomi/mimo-v2.6-flash` через AITunnel (OpenAI-совместимый API), тариф
30/120 ₽ за миллион входных/выходных токенов — как в практике недели 2.

**Что внутри.** Пять инструментов над базой Ростова (`tools.py`: `count_places`,
`find_places`, `top_brands`, `nearest`, `details`) с двумя вариантами описаний
(short — одна фраза, full — что делает / когда звать / когда не звать / единицы /
пример + описания полей); десять задач с эталоном из SQLite (`tasks.py`); цикл без
фреймворка (`agent.py`: лимит 8 шагов, ошибки как наблюдения, учёт usage и цены,
JSONL-журнал в `runs/`); метрики и A/B (`check.py`); тесты (`tests/test_assignment.py`).

## 1. Метрики основного прогона

`uv run python check.py --n 3` — десять задач по три прогона, вариант full.
Журнал: `runs/main_full_n3_*.jsonl`.

| Показатель | Значение |
|---|---|
| pass@1 (доля успешных прогонов) | **100%** (30/30) |
| pass^3 (задачи, прошедшие все 3 прогона) | **100%** (10/10) |
| Первый вызов: верный инструмент и аргументы | 96.7% (29/30) |
| Средние токены на прогон | 4744 (вход 4540 / выход 204) |
| Средняя стоимость прогона | 0.1607 ₽ → **0.48 ₽ на задачу** (3 прогона) |
| Среднее число шагов на прогон | 2.2 (лимит 8) |
| Ошибки среды / упёрлись в лимит шагов | 0 / 0 |

За 90 финальных прогонов (основной + A/B) ни одного `api_error`: помогает ретрай
запроса (до 3 попыток) и починка аргументов, которые провайдер иногда обрезает
(6–12 восстановлений на 30 прогонов — это баг адаптера AITunnel, восстановление
по content-дублю вызова, фиксируется в журнале флагом `repaired`).

## 2. A/B описаний инструментов

`uv run python check.py --ab --n 3` — short и full по три прогона на задачу.
Метрика задания — доля (задача × прогон), где **первый** вызов: верный инструмент
и верные аргументы. Журналы: `runs/ab_short_n3_*.jsonl`, `runs/ab_full_n3_*.jsonl`.

| Показатель | short (одна фраза) | full (полное описание) | Δ (full − short) |
|---|---|---|---|
| Точность первого вызова | 6.7% (2/30) | 100% (30/30) | **+93.3 п.п.** |
| Интервал Вильсона 95% | [0.02, 0.21] | [0.89, 1.00] | интервалы не перекрываются |
| pass@1 (ответ в итоге верен) | 93.3% (28/30) | 100% (30/30) | +6.7 п.п. |
| Средние токены на прогон | 4458 | 4482 | +24 (+0.5%) |
| Средняя стоимость прогона, ₽ | 0.1669 | 0.1516 | −0.0153 (−9%) |
| Среднее число шагов | 3.3 | 2.1 | −1.2 |

**Ответ числом: окупились ли лишние токены описаний.**
Полное описание стоило **+24 токена на прогон (+0.5%)** и дало **+93.3 п.п.
точности первого вызова**; интервалы Вильсона не перекрываются, разница значима.
Более того, в деньгах full дешевле: у short лишние шаги на самокоррекцию (3.3
против 2.1) съедают больше, чем экономия на коротких схемах (−0.0153 ₽/прогон).
Прирост идёт именно из-за перечисления допустимых значений `kind` латиницей и
границ применимости — короткая фраза «вид места» их не называет.

## 3. Три неудачные траектории

В финальных прогонах два прогона из 60 (A/B) дали неверный ответ и 30 прогонов
short провалили метрику первого вызова. Разбор — три худших случая; классификация
по заданию: не тот инструмент / не те аргументы / ошибка среды / зацикливание /
ложное «готово».

**а) `ab_short`, `brands_outpost`, прогон 2 — не те аргументы → ложное «готово»
(провал pass).**
Вопрос: «Какие сети пунктов выдачи чаще всего встречаются?». Short-описание не
говорит, что `kind` нужен латиницей, и модель первый вызов отправляет
`top_brands(kind="пункт выдачи")`. Инструмент вежливо отвечает строкой-ошибкой
«вида места нет в базе; есть: alcohol, antiques, …». Вместо того чтобы раскрыть
перечень и подобрать `outpost`, модель на следующем шаге подменяет вид на
`post_office` и уверенно выдаёт ответ с цифрами Почты России (62, СДЭК 14) —
вопрос был про пункты выдачи (Ozon, 183). Ответ неверный, `passed=False`.
Почему full так не делает: в полном описании перечислены допустимые значения и
случай, когда звать нельзя.

**б) `ab_short`, `find_outposts`, прогон 3 — не тот инструмент (провал A/B,
ответ после самокоррекции верен).**
Вопрос «Покажи пункты выдачи заказов» — это перечень, ожидается `find_places`,
а первый вызов (параллельно вторым) — `count_places(kind="пункт выдачи заказов")`:
и неверный инструмент, и неверный аргумент. На шаге 1 модель получает две
наблюдения-ошибки, на шаге 2 сама чинится (`outpost`), и за 4 шага даёт верный
ответ 922 и бренды. Метрика ответа засчитывает прогон, метрика первого вызова —
нет: лишний раунд общения и лишние токены как раз здесь и берутся.

**в) `ab_short`, `find_outposts`, прогон 1 — зацикливание (почти петля).**
Шесть шагов вместо двух: перебор вида «пункт выдачи заказа» → `post_office` →
параллельный счётчик → наконец `outpost`, и только потом осмысленная работа
(`find_places` → `top_brands` → четыре параллельных `details`). Прогон сошёлся
только потому, что лимит шагов — 8; при `max_steps=4` он был бы потерян. Это
та самая «ошибка в фильтре превращается в бесконечный цикл» из типичных ошибок
прошлых лет — спасает только явный предохранитель, а бороться с корнем надо
описанием.

*Ошибок среды (обрывы API) за 90 прогонов не было; единственный «почти-цикл»
слоился именно из плохих аргументов.*

## 4. Что делал агент, что проверял я

**Агент** (свой цикл, без OpenAI Agents SDK): по описаниям инструментов выбирал
вызов и собирал аргументы; наш код исполнял вызов и клал результат модели
наблюдением `role=tool`; любая ошибка (нет инструмента, битый или обрезанный
JSON, исключение) превращалась в короткое наблюдение «ошибка: …» — цикл не
падал, модель получала шанс исправиться; после 8 шагов без ответа прогон
закрывался статусом `max_steps`. Счётчики токенов брались из `usage` каждого
запроса, стоимость считалась по тарифу, каждый прогон писался строкой в JSONL.

**Я проверял**: эталон (ground truth) десяти задач считался из `poi.sqlite` без
участия модели — судья финального ответа сверяет число/название/часы с базой;
первый вызов сверялся с ожидаемыми инструментом и аргументами (`street` — по
подстроке, `lat/lon` — с допуском 1e-3°, `only_24_7` — строго по булеву значению);
pass@1, pass^3, доли и интервал Вильсона считает `check.py` по журналу; 12
pytest-тестов проверяют чистые функции (Вильсон, судьи, схемы short/full, починку
JSON) без обращения к API; три траектории выше читались вручную из `runs/`.

## 5. Воспроизводимость

На чистой машине (Python 3.12, есть `uv`):

```bash
git clone <репозиторий> && cd ai_course_mmcs_st
uv sync                          # зависимости
cp .env.example .env             # вписать OPENAI_API_KEY, OPENAI_BASE_URL, MODEL
uv run pytest                    # 12 тестов, без API
uv run python check.py --n 3     # основной прогон (≈5 ₽)
uv run python check.py --ab --n 3  # A/B (≈10 ₽)
```

Ограничения: три прогона на задачу — небольшая выборка, pass@1 100% на больших
выборках может слегка снизиться; разница A/B при этом настолько велина
(интервалы не перекрываются), что вывод устойчив.
